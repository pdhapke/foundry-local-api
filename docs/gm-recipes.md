# Generic GM recipe lookup and invocation

`foundry_gm_recipe_list`, `foundry_gm_recipe_search` and `foundry_gm_recipe_read` expose a fixed bounded catalog. Every entry is marked for lookup and includes purpose, triggers, required actual MCP tools, parameters, preconditions, steps, verification, permissions, recovery and exact version compatibility. Search accepts at most 200 characters and returns at most 25 entries. The API does not import Codex DM or its policy files.

`foundry_gm_recipe_invoke` accepts `schemaVersion:gm-actions-v1`, authenticated native `worldId/userId/sceneId`, recipe ID, stable original `idempotencyKey/correlationId`, latest `expectedInitialState`, and 1–12 explicit actions with unique step IDs. It calls the same descriptors exposed individually as MCP tools. It first validates every action with its native endpoint schema, then reads exact first-step state and rejects stale initial state. Each step applies once with the current snapshot and a SHA-256-derived stable key, validates receipt identity, independently reads back the resulting state, and stops at the first refusal or uncertainty. Already confirmed effects remain.

Combat creation readback changes to the created combat ID. Narrow session door/light/HP correction recipes use the existing `foundry_get_session_action_state` / `foundry_apply_session_action` contracts, including their atomic expected-state checks. Native activity, character, combat and scene recipes use the generic `gm-actions-v1` native operations. Activity use owns native consumption and, when in combat, activation-budget reservation/spend within the durable operation. Initialize budgets first; never debit again. Native activity supports explicit AOE placement through native AbilityTemplate geometry and BaseRegion._migrateMeasuredTemplateData into persisted Foundry 14 Regions; receipts retain regionId/Region UUID/native shapes and original template geometry with author/current-level/origin proof and existing output IDs for partial recovery. It also supports eligible native summon profile placements, and one-action held-spell ready/release phases with original cast receipt/resource identity; modern Region behaviors, linked/wildcard/compendium summon preparation and ambiguous held profiles require native controls. Damage/save application remains explicit. Character operations include stable/unconscious status, temporary maximum HP, native attunement, real item copy/removal, XP and exported CurrencyManager conversion; transfers retain partial receipts rather than claiming atomicity. This is a primitive workflow dispatcher, not a D&D rules engine or an autonomous event scheduler.

All 14 entries are executable when their named tools are registered. `toolsAvailable` and `executable` report that registration. Document preparation accepts bounded native `get/list/update` steps for existing real source documents; exact authenticated requester, parent/scene identity, revision and independent source readback are checked. It rejects create/delete, security/ownership/scripts, nested document collection replacements and token x/y/elevation updates that would bypass native movement budgets. Existing native import/create preparation remains a separate explicit workflow.

TV steps are `{tvUserId,tvClientId,action:inspect|unionVision|camera|calibrate|perspective,...}`. The dispatcher injects the exact authenticated `requestingUserId/worldId/sceneId`, requires one TV throughout, compares current `{sceneId,x,y,scale}` and verifies independently read native PC union. Camera accepts `{x,y,scale}`; calibration accepts actual `{measuredPixels,measuredInches,gridInches,rulerConfirmed:true}`; perspective is only `native-top-down`. Native OBSERVER permission must already exist; missing sources block, and this feature grants no permission. Native walls/fog/detection remain authoritative. Physical calibration retains `physicalVerified:false` pending later human ruler acceptance.

Session/document/TV invocations first persist a journal-only `recipe.reservation` through the same `foundry_gm_scene_state/apply` tools; `data.reservationOnly:true` and exact native identity/readback are required. This marker changes no gameplay state. Native atomic admission rejects an existing marker even when concurrent fresh transports both observed a missing key; only the admitted invocation can dispatch later stages. Its stable key is `recipe-reservation-` plus SHA-256 of the canonical `[worldId,userId,originalInvocationKey]`; its action retains recipe ID and SHA-256 of the complete canonical request. Fresh invocation inspects this key with `foundry_gm_receipt_read`: retained reserved/terminal identity stops all later stages even if a no-op left source/camera state unchanged. Native gameplay families similarly inspect every original per-step key. Only the exact live endpoint cache returns prior results without dispatch.

The process-local recipe receipt cache retains at most 4,096 original keys without eviction. A live exact retry returns the cached original result after a fresh native authority read. A changed fingerprint under the same key is refused. Restart does **not** automatically resume or reconstruct a multi-step recipe. Changed initial state refuses a restart invocation; inspect the durable native per-step records using `foundry_gm_receipt_read` (including the recipe reservation marker for session/document/TV workflows), then reconcile explicitly. Never replace IDs to reroll, respend resources, compensate or continue an uncertain stage. Transport credentials do not grant native world/user authority.

All mutation tools remain native-authorized. The Codex DM composition additionally requires an explicit authenticated GM IC request, exact task scene, configured mutation allowlist, any configured approval and no unresolved world quarantine. Browser observation hints cannot invoke new gameplay; the host remains snapshots-only. No source build changes installed assets, native security or live game state.

Offline tests cover list/search/read, bounded schemas, exact invocation, no duplicate spends, stale state, changed fingerprints, stop-on-failure/uncertainty and restart fences. Native hardware/LAN/provider/gameplay acceptance remains a separate authorized deployment gate.

Fresh generic native recipe runs now inspect every original per-step key with `foundry_gm_receipt_read` before dispatch. Without the exact live recipe cache, any reserved or terminal native step returns reconciliation-required and stops all later stages, including when a roll left actor state unchanged. Missing/invalid lookup fails closed. This fence supplements the original-state comparison and companion durable reservations; it never automatically resumes a missing step.
